# 自动更新维护

客户端从 1.1.1 起改用每用户 NSIS 安装版。appId `com.yuntu.workbench`、包名 `yuntu-workbench`、产品名保持不变，本机设备标识与任务进度仍使用原用户数据目录。第一次从免安装版迁移需要安装一次，以后使用桌面或开始菜单快捷方式。

## 员工侧

启动后自动检查，每小时再检查一次；有新版时后台下载。标题栏显示当前版本、下载进度和“重启并安装”。上传、散列或图片处理期间不能安装，主进程也独立检查并阻止竞态。普通退出不自动安装。

安装前保存界面检查点并刷盘，保存失败或超时会保留当前程序并显示错误，可重试；不会强行跳过。更新下载失败不影响原有传图操作。网页端没有桌面更新按钮。

## 存储和权限

更新桶 `yuntu-workbench-releases` 通过 `RELEASES` 绑定，独立于图片桶及七天清理任务。更新下载地址：

`https://yuntu-workbench.gy1207981728.workers.dev/updates/stable/`

仅公开固定名称的安装包、blockmap、latest.yml；支持 GET/HEAD 和单段 Range。安装包与 blockmap 不允许覆盖，latest.yml 禁止缓存并最后发布。保留旧版文件供差分更新使用，不要直接删除仍在使用的旧包。

发布使用独立的 `RELEASE_PUBLISH_TOKEN` Worker Secret，普通员工和软件管理员会话都不能发布。凭据只保存在开发机私有配置文件，不能提交 Git、放进安装包或发给员工。私有配置包含 `baseUrl` 和随机 64 位十六进制 `publishToken`；生产 Secret 必须与该值一致。原有 `CONFIG_KEY`、`SETUP_TOKEN` 仍须保留。

## 发布步骤

1. 按十进位更新项目版本、锁文件及服务端版本，完成测试和构建。
2. 构建 NSIS：`npm run pack:win -- --config.directories.output=<版本输出目录>`。
3. 输出应有 `Yuntu-Workbench-Setup-X.Y.Z-x64.exe`、对应 `.blockmap`、`latest.yml`，以及配置了通道的 `win-unpacked/resources/app-update.yml`。
4. 运行 `node scripts/publish-release.mjs <版本输出目录> stable <开发机私有配置.json>`。
5. 脚本先核对本地 SHA512/大小，以 8MiB 分块上传，重新从公开地址完整读取核验后，最后原子发布 latest.yml。中途失败可以重跑，同一输出目录的 `.publish-stable.json` 保存上传断点，不应提交源码。
6. 核验元数据及实际自动更新；最后同步 GitHub 源码。

客户端无发布凭据。不要把发布接口改成普通管理员账号授权，不要对未校验的文件提前更新 latest.yml。已发布的文件不可覆盖；修复发布内容必须递增版本号。

独立验收使用 `acceptance-*` 通道与独立应用身份，不切换 stable、不访问生产账号数据。临时验收入口明确从正式安装包排除。
