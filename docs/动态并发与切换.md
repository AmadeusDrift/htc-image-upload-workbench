# 1.1.2 动态上传并发

当前阶段仅本地隔离开发。未部署 Worker、未迁移生产 D1、未更新 stable 更新源。

## 行为

- 继续使用原员工账号、密码、权限、业务组和任务归属。多台电脑可使用同一账号，各自参与分配。
- 公司同时有效上传授权最多 20 个。按设备均分：1 台 20、2 台各 10、3 台 7/7/6、4 台各 5。三台设备中余下两个名额按设备标识排序分配。
- 分配在授权 INSERT 的同一个 SQL 快照内检查，避免先查额度后插入导致超发。同一文件最多一个授权。
- 新设备加入时已有传输继续，超过新份额的设备等待原传输完成后让出名额，不撤销正在使用的授权。
- 仅登录、查看文件或打开软件不登记上传需求。新客户端开始任务时登记本次运行标识，申请授权时刷新需求；结束或暂停时关闭本次运行。
- 等待授权的客户端每 2 秒重试。需求 30 秒不刷新即过期；已有有效授权的设备继续计入，兼容无心跳的旧客户端。
- 异常退出时，未能正常释放的上传授权沿用原有 5 分钟过期机制。公开图片地址、7 天保留策略不变。
- 已关闭运行保留一天的停止标记，防止暂停后迟到的启动/授权请求重新占位；恢复任务会产生新运行标识，原任务 ID 和图片标识保持不变。旧客户端无运行标识，仍沿用授权申请和超时机制。
- 超过 4 台也可参与分配，不增加公司总额度；超过 20 台时每台最多一个授权并等待空位，不承诺严格的轮转顺序。
- 客户端最多 20 个上传候选等待授权；哈希仍最多 5 路，原生上传层最多 20 路。服务端授权是最终约束。

## 数据兼容

`server/migrations/0003-upload-demands.sql` 只新增需求表及索引，可重复执行。保留旧 users、tasks、files、leases 全部记录和字段。

本地进度的应用 ID、userData 路径、schemaVersion、ownerId、任务 ID、clientId、源文件路径格式都不变。继续使用原账号恢复原任务；恢复时先核对服务器成功记录，跳过已成功图片，不另建任务。

旧客户端可继续用原 API 上传，但其本地仍最多发起 5 路。新客户端连接旧后端时也受旧的固定 5 路限制；因此完整动态分配需要后端和客户端都更新。

所有服务端测试使用 Miniflare 本地临时 D1/R2。测试覆盖 20 上限竞争、同账号多设备均分、加入时让额、暂停释放、异常超时、旧客户端、重复文件、增量迁移和旧队列恢复。大批次 16,000/20,000 用例是元数据/模拟传输测试，不代表四台实体电脑的实网速度。

本地构建的安装包默认仍配置生产服务地址。尚未执行线上切换前，不安装或启动它去跑公司任务，也不发布到自动更新通道。

## 待授权切换时的顺序

1. 通知各电脑暂停，等待传输停止并成功保存本地队列；正常退出，不清空、不卸载、不移动原图片。
2. 核对在线上传授权；备份原后端版本、D1 元数据和各设备本地进度，再执行增量迁移。不能用示例 `.dev.vars` 覆盖生产密钥。
3. 部署已核验的后端，先验证健康检查、原账号读取、旧任务和旧图片链接。完整保留原绑定与生产密钥。
4. 发布安装包与 blockmap，校验公开下载的字节与 SHA512，最后更新 latest.yml。
5. 选一台原电脑更新，使用原账号继续原任务；确认成功跳过、任务 ID 不变后，再更新其他电脑。
6. 实测 1→2→4 台动态分配与暂停释放。线上版本检查与检查点恢复通过后才认为上线完成。

若需回滚后端，新增表可保留，旧后端不会读取它；旧的总 20/每账号及每设备 5 限制恢复生效。保留任务与原文件，不删除或重置数据。已发布的不可变安装包禁止替换，客户端回退需单独设计版本发布。
